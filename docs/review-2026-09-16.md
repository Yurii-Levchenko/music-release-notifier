## Resilience & Concurrency

### Findings (most severe first, max 15)

1. [high] [CONFIRMED] Graceful shutdown mid-send delivers the message but leaves the row pending → duplicate after restart
   - Where: `internal/notifier/notifier.go:272-299`; `cmd/releaseradar/main.go:49`
   - Evidence: `sendErr := channel.Send(ctx, …)` then `n.queue.MarkSent(ctx, p.ID)` with the same (now-canceled) gctx; telego's caller checks `ctx.Done()` only *before* the request (`telego@v1.11.2/telegoapi/caller.go:32-36`), so an in-flight request completes.
   - Failure scenario: SIGTERM during one HTTP round-trip → Telegram returns 200 → `MarkSent` fails instantly on canceled ctx ("delivered but could not mark sent") → row stays leased → re-claimed ≤5 min after restart → user gets it twice. Deterministic whenever a drain is in flight. Telegram has no idempotency key, so the same residual risk exists for a response lost after Telegram accepted (bounded only by lease 5 min × no ceiling: `Claim` has no `attempts < max` guard, `notifications.go:104-117`; the ceiling is enforced only on the Transient path).
   - Fix: record outcomes with `context.WithoutCancel(ctx)` + 5 s timeout; stop claiming once `ctx.Err() != nil`; add `AND n.attempts < $3` to the `due` CTE.

2. [high] [CONFIRMED] Telegram sends have no timeout and cannot be canceled
   - Where: `internal/telegram/client.go:36,83-91`; telego `bot.go:105` (`FastHTTPCaller{Client: &fasthttp.Client{}}`), `caller.go:60-64` (`Do` when ctx has no deadline).
   - Failure scenario: sendPhoto hangs (Telegram fetching a slow cover) → single drain loop stalls indefinitely; the 5-min lease cannot help because the only claimer is the stuck one; only the 5-min notifier budget notices. On SIGTERM the hang outlives compose's default 10 s grace (`srv.Shutdown` 15 s at `main.go:270` is also > 10 s) → SIGKILL.
   - Fix: `context.WithTimeout(ctx, 30*time.Second)` per send in `Notifier.Send`, and `stop_grace_period: 45s`.

3. [high] [CONFIRMED] Bot heartbeat is timer-gated, so a deaf long-poll keeps the dead-man's switch green
   - Where: `internal/telegram/bot.go:155-156` (`case <-alive.C: b.beat()`); telego `long_polling.go:125-134`.
   - Evidence: telego logs and retries `getUpdates` every 8 s forever and never closes the channel; `getUpdates` uses the same deadline-less fasthttp path.
   - Failure scenario: 401/409 after start, or a hung TCP connection → no updates ever → channel stays open → bot beats every minute → heartbeat pings. Exactly the case `health.go:9-14` claims to catch.
   - Fix: beat only when `GetUpdates` succeeds (own polling loop with per-call deadline), or `WithLongPollingRetryTimeout(0)` so errors close the channel and the existing "polling stopped unexpectedly" path (`bot.go:170`) fires.

4. [medium] [CONFIRMED] Retry ceiling ≠ SPEC §10/§11; 12h step is dead; outage budget ≈ 2h36m, then permanent silent failure
   - Where: `internal/storage/notifications.go:116-117,178,270-285`

   - Fix: `maxDeliveryAttempts = 6`; alerts on `increase(notifications_total{disposition="transient"}[1h])`, `telegram_requests_total{code="401"}`, and a `failed` gauge.

5. [medium] [CONFIRMED] Head-of-line blocking in the bot loop
   - Where: `bot.go:172` (`b.handle` inline); `subscriptions.go:130` (MB lookup 60 s × 5, `musicbrainz/client.go:58,71`); `catchup.go:153-160` (LB fetch 2 min × 4 under a mutex).

## Decisions needed from the owner

These are product or security policy, not engineering judgement, so they are not decided here.

1. **What does a block mean?** (Spec #2, Resilience #7.) Today a block detected via `my_chat_member` keeps subscriptions (reversible flag; user unblocks and their list is intact) while a block detected via 403 on send deletes them. SPEC §10/NFR-7 say delete. Options: **(A)** block = reversible flag, deletion only on `/stop` or a hard 403 — change the spec; **(B)** any detected block deletes subscriptions — change `SetBlocked(true)`. Recommendation: A. Unblocking is ordinary behaviour and C30 is about *requests* to delete; either way `SetBlocked(true)` must also park pending rows so the queue metrics stop counting them.
2. **Confirm-on-redeem and `/unlink`?** (Security #5.) A typed code binds *whoever minted it* to the typist's account with no confirmation and no way back except `/stop`. Recommendation: yes — an inline Yes/No before `Redeem` (checking `cq.From.ID`) and an `/unlink` command. Cheap, and S9 makes the bearer far more valuable.
3. **Backups at rest.** (Security #8.) Plaintext `pg_dump` custom-format archives in `./backups`, written by root. Recommendation: rely on BitLocker on the laptop now; encrypt with `age` before the VPS move, key held off-box. Also write into SPEC C30 that deleted users persist in dumps for `BACKUP_KEEP` days.
4. **Bot concurrency model.** (Resilience #5 + corroboration row 1.) Per-update goroutines behind a semaphore with a per-update timeout removes head-of-line blocking and shrinks the DoS surface, but it is an architectural change to the bot loop. Recommendation: before S9, because S9 adds a second entry point that would otherwise inherit the same single queue.
5. **The `Notifier` boundary refactor.** (Standards #1.) `Pending` gets `Kind`/`Address`, `For(p.Kind)`, pacing by address, `CatchUp` by user id. Recommendation: before S9 for the same reason — S9's `POST /subscriptions` would otherwise be the third place `chat_id` is threaded through the domain.
